# Bind verified WeChat proof to an existing account

Date: 2026-10-18. Status: implemented authentication foundation; live WeChat, device and complete mobile business acceptance remain separate. Extends FR01 and the account/school boundaries in ADR 0008. D02's one-AppID/two-workspace shape was confirmed on this date; D01/D06 and actual platform setup remain separate.

A WeChat identity is a login method for an existing KnowPulse account, never a school membership, guardian grant or client-selected user. The authenticated Web account confirms its current password and ownership before receiving a random, five-minute binding code. Expected account/tenant fields only reject a switched Web session. Password failures commit the existing Identity lockout counter independently of a rejected binding operation. Issuance replaces older pending codes and cannot replace an active binding; the owner must explicitly unlink it first. Passwordless/federated step-up and school invitation/recovery are not introduced by this slice.

The anonymous exchange requires both that code and a fresh server-verified WeChat login proof for the configured AppID. It derives the account and tenant from the recorded code, never from submitted user IDs or roles. A bound record accepts a retry only for the same verified subject, even after the original code expired; a different subject cannot take it over. A new credential requires another fresh proof. Only hashes of the code secret, app-scoped subject and account security stamp are stored; raw openid, session_key and AppSecret do not enter business DTOs, history or general audit. The server adapter has a fixed HTTPS destination, no redirects, bounded reads, a ten-second deadline covering headers and body, and controlled errors without vendor response bodies or credential-bearing URLs.

Each enabled app has a public OpenIddict client limited to `urn:knowpulse:wechat`, the KnowPulse API scope and token revocation. The standard secret-redacted `code` field carries the fresh proof. The grant creates claims from the actual server account and retains only public identity/role/tenant claims, API scope/resource and the binding reference. It issues a five-minute access token with no refresh token. Tenant requests use the trusted exchange receipt's standard tenant header. Caller identity fields do not select an account or a school role.

Every business request carrying a WeChat binding claim rechecks the actual persisted OpenIddict token status/subject, active binding, enabled unambiguous app, account tenant/activity/lockout/security stamp. Standard revocation blocks that session; Web unlink blocks all tokens from that binding. Configuration removal and password/security-stamp changes also close later requests. Existing cookie and other bearer flows keep their existing rules. The endpoint IP limiter is per process; a multi-host public launch needs a trusted proxy and distributed limit. In-flight authorized operations and copies already delivered cannot be recalled.

Bindings use a retained relational aggregate, unique nullable active account/app and subject/app keys, tenant-aware queries and account compare-and-swap. Revocation releases active keys without deleting history. The custom repository converts uniqueness races to a controlled failure. Migration `20261017223739_AddVerifiedWeChatAccountBindings` adds no historical binding and refuses downgrade once any record exists. Binding history is private, counted and paged before projection; it does not expose subject or secret hashes.

The native project stores verified binding/account/tenant identifiers; its bearer token stays in memory. Feedback recovery additionally stores only scoped operation identifiers under ADR 0018, never body text. Explicitly acknowledged assessment drafts and exact pending commands use their separate private local storage under ADR 0027, never this binding record. A fresh login is needed after process loss. Logout clears local session state immediately, drops private editor memory, attempts private answer/cache cleanup and standard server revocation; cleanup and revocation failures are reported separately, without a physical-erasure promise. Account generations and request versions reject late responses and clear stale role views on authorization failure. A narrow allowlist of education mutation paths and editing-rule codes distinguishes ABP's business-rule 400/403 from authentication/authorization denial, so expired attempts, content validation or response-set conflicts do not erase drafts. Other 401/403 responses retain the original denial behavior. Native screens include login, workspaces, teacher assessment progress, five-type student answering and submission review, student result reading, manual teacher feedback and exact-version student feedback reading. Complex grading and final result release remain in Web under FR18. These screens do not satisfy the full EDU-M3 business scope.

On 2026-10-18 the user settled D02's product shape: one AppID with separate teacher and student workspaces. Workspaces use the current verified school identities, never a selected role or separate application to grant authority. Existing server alias support does not imply shipping multiple mini programs. The user requested code and local verification first; actual WeChat authentication/domain configuration is not yet available. AppID/secret configuration remains empty and disabled until configured, and synthetic local proof is not live WeChat acceptance. The native client never contains a secret or account password. Lost binding metadata is recovered through the authenticated Web unlink/rebind flow; no anonymous account discovery or automatic account creation is exposed.
