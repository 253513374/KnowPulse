# Publish education assessments with immutable revisions and fixed student recipients

Education assessment tasks are teaching facts separate from personal materials and enterprise exam plans. A teacher owns a task; each explicit draft save and publication creates an immutable `EducationAssessmentTaskRevision`. Stable operation IDs identify revisions and record request fingerprints. The aggregate advances its current pointer under the concurrency stamp the teacher saw. Publication refers to the confirmed draft and roster preview, creates a new published revision and freezes all recipients in one relational transaction. Existing receipts remain recoverable independently of a later draft or publication.

Create and save return the latest task workspace, including when the same operation is replayed after another save. `GetOperation` returns the exact immutable revision for the specified operation; publication replay returns that original published revision directly. Clients use the operation receipt to resolve an unknown write result and the task workspace to continue editing, rather than treating a later current revision as the earlier operation's content.

The first implemented flow targets one effective teaching assignment and its class. It supports that class's checked students or a specified subset, never organization `All`, department or position assignment. The roster records actual identity, school membership and enrollment pairs. Preview alone grants no access; publication rechecks the roster and effective account, school, term, class and subject relations using existing school and account concurrency barriers. A changed preview cannot silently publish to different students. Limits such as 3,000 recipients are current development protection, not school capacity commitments under PRD D09.

Publication and student start acquire the shared school write barrier before student account write barriers. Publication may capture account baselines earlier, then validates its paper and current curriculum/source usage under the school barrier before updating student accounts in ID order and confirming the roster again. This keeps publication and start from acquiring the same school and student roots in opposite order; all checks and new facts remain in the caller's relational transaction.

Publication reuses independently saved `ExamPaper` snapshots and their approved definition revisions. The teacher explicitly previews and confirms the frozen version. Editing a source question or approving a later definition does not itself revoke an already approved frozen version or substitute new content into that paper. New publication must still prove its frozen content, scoring rules, curriculum allocation and provenance match the referenced approved revision, and recheck current teaching scope and source usage rights. A deleted, disabled or archived original question blocks new publication. Choosing changed questions requires a new saved paper and publication confirmation. This does not settle PRD D03's policy for source withdrawal after a task is published.

Frozen point allocations are compared by mapping identity and decimal values, not JSON formatting. Canonical approval serialization may normalize trailing zeros; `1.00` and `1` represent the same weight, while a different mapping, weight or score still fails validation.

Student access uses a fixed recipient plus the currently checked account, student membership and class enrollment, not the teacher-only curriculum guard or personal paper ownership. Listing or reading a task does not start an attempt. An explicit start creates or recovers the same `EducationAssessmentAttempt`; the recipient concurrency stamp and unique `(RecipientId, AttemptNumber)` protect the winner. Its deadline is the earlier of the task deadline and server start plus duration. UTC intervals are half-open, so an operation at the deadline is already late. Restoring an attempt never changes its start or deadline.

New education attempts do not reference `ExamPlan`: that existing model is coupled to organization assignment and legacy objective scoring. Student DTOs contain only their task and the question surface needed to answer. Configured result rules are distinct from the currently effective result visibility, which stays hidden until the real grading and task-release use cases exist. No allowed answers, reference answers, scoring points, private provenance or teacher-only curriculum structures enter the new nested student models.

This decision covers task revisions, fixed recipients and explicit start/recovery. Structured responses, picture attachments, submission and background cutoff sealing, full scoring evidence, manual grading, final task release, exceptions, notifications and real WeChat clients must continue under PRD FR14–FR34. The first flow is not a complete examination. Published-time/roster changes, additional attempts and cancellation require their own recorded use cases; this slice does not expose empty actions for them. History access after relation changes remains governed by PRD D06 rather than implied by ownership alone.

The decision extends [ADR 0013](0013-explicit-question-scoring-and-approved-definition-revisions.md) and preserves the tenant-scoped school facts in [ADR 0008](0008-account-owned-libraries-and-tenant-scoped-school-facts.md), provenance in [ADR 0009](0009-version-bound-school-sharing-and-source-provenance.md), and the current-use barriers in [ADR 0012](0012-confirmed-material-mappings-and-recoverable-curriculum-generation.md). Old enterprise plans and attempts keep their original semantics.

## Exclude draft instructions from generic audit parameters (2026-10-18)

A real isolated workload setup detected two synthetic instruction bodies in generic CreateDraftAsync audit parameters. Draft creation and saving share EducationAssessmentDraftContentDto, which is now included in the Host audit ignored-types policy. The current [ABP 10.6 AuditingHelper](https://github.com/abpframework/abp/blob/10.6.0/framework/src/Volo.Abp.Auditing/Volo/Abp/Auditing/AuditingHelper.cs) applies that policy to instances of derived input types, so one entry covers both actual commands without disabling the operation audit. Business revisions and authorization remain intact; saving still retains its root identifier in the action parameters.

The same disposable database preserves the two pre-fix synthetic marker occurrences. Post-fix real create and save both store the intended body in the private business draft, while both new audit inputs are null, the save root remains auditable, and no new marker occurs in generic audit/history/URLs or Host logs. This change stops future parameter-body capture; it does not silently rewrite existing audit history or settle production retention policy. Isolated fixture cleanup happens only after recording that distinction.
