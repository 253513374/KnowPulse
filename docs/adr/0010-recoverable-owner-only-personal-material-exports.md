# Keep personal material exports owner-only and recover their artifacts

Personal material export is a durable operation owned by the existing account and its default library. A client operation ID is the job ID; repeating it returns the same authorized job. The application service explicitly checks the personal-library permission, current account, tenant and immutable owner/library pair. It does not accept another owner or shared-material input. Operators and school roles do not override ownership.

The HTTP host consumes persisted jobs in small sequential batches through an internal processor, following the existing worker and unit-of-work patterns without exposing the processor as a remote application API. Processing captures undeleted own items, all their versions including archived versions, and original attachments. The source manifest stores only identity, parent and concurrency references. The ZIP contains readable content and metadata plus original attachment bytes with safe ID paths and extensions; it does not contain provider paths, credentials, exam answers or student teaching records. Actual source bytes, output size and record counts have configurable limits. These are development defaults rather than school capacity commitments.

An execution has its own run ID, heartbeat and output target. Completion requires a successfully stored ZIP and a final authorization and source-consistency check. Source changes or storage failures retain a controlled failure stage/code and permit an explicit retry using a new source snapshot. New pending work has priority over old completed checks. A completed file is downloadable only before expiry and after current permission, account, library and source checks. Cancellation stops application access; it does not recall downloaded copies.

Cancellation and heartbeat expiry are not proof that external writes have stopped. The job retains current and retired run cleanup targets until their writers have confirmed stopping. A retry must preserve an old target when it starts a new run; an old executor finishes and cleans only its own run. Unknown stop state retains a retryable cleanup target rather than assuming a lease or an operating-system file lock guarantees safety. Temporary ZIP and output Blob cleanup never delete original attachments, and failed cleanup preserves its recovery facts.

This extends personal accumulation under ADR 0008 and does not change the indexing retry lineage in ADR 0006 or version/use-bound school sharing in ADR 0009. School-shared exports remain unsupported until separately implemented with their use authorization and D03 policy. Data retention, account exit and deployment capacity remain PRD D06/D09 decisions; implementation tests do not substitute for real-provider, concurrency or logged-in UI acceptance.
