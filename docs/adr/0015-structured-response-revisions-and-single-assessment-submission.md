# Preserve structured response revisions and seal one education submission

Education responses belong to an `EducationAssessmentAttempt`, its student and its frozen paper question. They do not reuse the enterprise `ExamAnswer` normalization, client-version advancement or immediate objective scoring. A complete single-question response preserves option order, stable blank IDs with original text, subjective text and ordered image references with rotation. Unknown or duplicated identities, incompatible fields and unconfirmed images are rejected rather than normalized into a valid response. The project-owned bounded JSON value has an explicit schema; no provider types enter the domain or contracts.

Each save operation creates one immutable `EducationAssessmentResponseRevision`; its ID is the stable operation ID and its fingerprint, original response, hash, observed/result version and UTC confirmation time are the exact receipt. One current-response pointer exists per attempt and frozen question. Saving advances the attempt's global response version, current pointer and immutable revision in the same relational transaction under the observed version and aggregate concurrency stamp. Replaying a save recovers that revision, independently of later current answers; changed input cannot reuse the operation. Different devices or questions may conflict on the global version. The first client must recover the latest confirmed state and explicitly retry, rather than silently merge stale inputs. A batch operation parent is unnecessary until actual multi-question atomic saves are required.

An image upload has its own stable `EducationAssessmentAnswerAttachment` fact. Its frozen tenant/student/attempt/paper/question, expected bytes/hash, name, detected type and Blob location are persisted before the external write. Only a successful, currently permitted completion advances pending to uploaded. An unknown outcome retains that location; a matching retry verifies the existing bytes and can complete the same upload. Queries report the persisted state without changing it. Upload success is separate from inclusion in an answer: the response revision freezes ordering, replacement and rotation, and pending images never enter an effective response. Blob files are held in the education answer container, separately from private knowledge materials. History never depends on deleting or rewriting a previously referenced original image. Development byte/count limits are protection, not school capacity or retention promises under PRD D04/D06/D09; complete temporary cleanup and retention policy require their own use cases.

All editing and sealing paths acquire the same attempt CAS barrier before choosing their effective confirmation or closing UTC instant. A read or blocked update can cross the deadline, including when the blocking transaction eventually rolls back without changing the original stamp; a timestamp captured before that wait cannot authorize a late save or label a cutoff as manual submission. Read-only recovery does not rotate write stamps: it verifies the response set and submission pointer again after reading their immutable values, and a changing set is boundedly reread rather than returned as one mixed version.

Manual submission and server cutoff call one concrete sealing use case. The attempt CAS, a unique submission per attempt and a paired submission/version pointer freeze the manifest of all paper questions, using their current confirmed response revisions or explicit unanswered entries. A manual operation checks the paper and response versions and requires a deliberate saved-only confirmation for incomplete content. Client-only or still-uploading content is excluded, not labeled received. At or after the half-open UTC deadline, sealing records the actual cutoff cause and effective deadline; it does not backdate a late manual answer. The actual seal time remains separate. Competing or repeated entry points return the one committed winner, without pretending that another operation created a new submission.

Student saves, uploads and manual submission recheck the current account and fixed recipient with its current school/student/enrollment facts, using the school-before-account barriers from ADR 0014. The deadline worker first lists bounded due attempts across recorded tenants and then processes each in its own tenant scope and transaction. It verifies the existing published revision, fixed recipient and frozen paper facts without requiring a logged-in student, the teacher's current textbook or an unexpired membership. Otherwise leaving the client or ending a relation could prevent server cutoff forever. This background authority grants no reading permission: late/submitted recovery endpoints still validate the requesting student's current access and expose only safe paper content, their original answers and their receipt.

A partially answered fill-blank question remains incomplete when a frozen blank is missing or has only whitespace, even when another blank contains text. The shared sealing use case checks those identities against the frozen question; manual submission without saved-only confirmation is rejected, while cutoff still seals the confirmed portion. Correctness and grading are separate from completeness.

This extends [ADR 0014](0014-education-assessment-revisions-and-fixed-student-recipients.md). Actual student editing controls, weak-network local persistence, multi-host races and real WeChat behavior need their own acceptance. Submission alone does not grade a paper or release results; FR16/FR17, full per-question evidence, comments, analysis and the EDU-M1–M4 teaching loop remain separate required work.
