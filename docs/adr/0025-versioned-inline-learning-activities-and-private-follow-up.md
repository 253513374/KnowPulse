# Version inline learning activities and separate student progress from private follow-up

Date: 2026-10-17. Status: accepted for the service and compiled Web slice. This extends ADRs 0023–0024; it does not complete material-version access or formal reassessment binding.

Follow-up: [ADR 0026](0026-bind-exact-formal-assessments-to-published-plan-activities.md) adds exact formal diagnostic/reassessment bindings, real submission-derived progress and context corrections. The original deferred scope below records this slice's historical boundary.

Further follow-up: [ADR 0030](0030-freeze-activity-material-grants-and-explicit-student-use.md) adds frozen exact material references, selected attachment access and source-withdrawal blocking. Current availability can mark an activity blocked while preserving its submitted completion/history; workload still uses actual student completion facts. Independent learning tasks remain separate work.

Workload follow-up: [ADR 0034](0034-unified-student-learning-schedule-and-workload.md) adds a separate current schedule across plans, independent study, corrections and formal assessments. This ADR's original plan-only endpoint remains compatible; its semantics are not silently expanded.

Teacher mobile follow-up: [ADR 0046](0046-native-teacher-plan-progress-and-private-follow-up.md) adds the native teacher metadata list, exact-publication progress and owner-private difficulty handling. The activity contract now has fourteen operations; the original Web/student operations and command fingerprints remain compatible. Historical deferred statements below describe their original slice.

Publishing a confirmed plan now creates an activity for each frozen step in the same relational transaction. Identity includes the exact public plan revision, step and student. Saving/confirming a draft creates no activities. New publications have new assignments and do not copy an earlier completion into changed instructions. Teacher progress can select past published versions and retain their original events after replacement or withdrawal.

For a pre-existing current publication, an authorized read may reconcile its missing activities under the same authority barrier. Their assignment time is the actual creation time, not a guessed historical publication/delivery time. A historical or withdrawn version is never retroactively assigned through this read. Actual authorized plan-body delivery marks first provision, including the existing student plan-opening endpoint. Lists, workload totals, waiting responses and teacher progress do not mark provision. Provision is not reading, engagement or completion.

## Student facts and teacher handling

Student actions are start/restart, self-reported activity completion and explicitly submitted difficulty. Complete requires an actual start and an explicit activity-only confirmation. Reported minutes are optional and self-reported, not measured attention. Restarting a completed activity requires a shared explanation. A later difficulty changes current progress to blocked while retaining completion history; a blocked learner is not forced to claim completion.

Diagnostic and reassessment steps cannot be completed through this self-report API. They require future exact formal assessment bindings and new-question checks. Activity preparation does not start an exam, create a submission or contribute independent evidence. No activity table is read by scoring or mastery calculations.

Text is explicitly submitted to the plan's teacher with sharing confirmation. It is a separate teaching fact, never an implicit copy of a private note. A learner can report unclear instructions, insufficient time, unavailable material or another difficulty. A known, actually provided current activity can accept difficulty even when a changed source or result gate withholds the plan body. Starting/completing still requires current authorized content; an unprovided, superseded or withdrawn activity cannot accept new execution or difficulty. A past committed operation remains recoverable after replacement/withdrawal while the student's current school relations remain authorized.

The author records private handling of an exact current student difficulty. Explicit confirmation acknowledges that only the handling time is visible to the student. The note is teacher-private; sending pedagogical feedback uses the existing confirmed feedback workflow, with its own delivery and hint-context controls. This avoids creating an untracked new public answer channel. Handling never completes an activity, resolves a new difficulty by accident or marks mastery. A subsequent student report has no matching handling until the teacher records one for that exact report.

## Authorization, versions and histories

The existing plan service explicitly exposes the new activity contract using the same multi-interface registration pattern as assessments. Nine operations provide teacher progress/history/handling/recovery and student progress/actions/history/recovery/workload. Teacher operations require TeachingPlanManage and AnalysisManage plus current author/teaching/student relations. Student reads require TeachingPlanView and caller-derived identity; writes additionally require LearningParticipate. No client-supplied student identity grants access.

Writes use immutable operation revisions, request fingerprints, expected heads and the existing school/account barriers. Re-read plan and activity heads after acquiring the barrier; a pre-lock read must not authorize a stale history page. Teacher writes require the current whole-activity revision/stamp and exact student report. Student writes compare only their own revision head, so an authorized private teacher update does not invalidate an unchanged student command. The append still uses the root's internal CAS and monotone journal sequence.

The student sequence and head are separate from the whole journal and teacher-handling pointer. Public values explicitly exclude private teacher operation IDs, notes, whole-journal counters/stamps and fingerprints. Teacher handling therefore does not fabricate a student progress revision. Original-operation retries recover before current-version rejection and never roll a later state back. Same-ID different requests and stale new writes are rejected.

Teacher history is paged against an expected whole-journal head. Student history contains only that student's submitted actions and uses the expected student head; a private handling update does not change its count/page version. Past owned student records can be read under current school authority without reopening old plan bodies or teacher notes. Full cross-version student history discovery and school historical-access/retention policy remain separate work.

Progress is derived from the current student action; assignment/provision and handling are separate facts. The teacher Web selects published versions, views completion/blocked counts and submitted history, and records private handling. The student Web starts/restarts activities, confirms activity-only completion, submits difficulty and reads their submitted history. Both retain exact pending commands in account/tenant/plan-scoped session storage before writes, recover/resend the original operation and guard navigation/discard.

## Workload, persistence and scope

The student workload query groups remaining estimates across accessible current plans by subject label and due date in UTC, within a half-open window of at most 31 days. Completed activities are excluded. Waiting, withdrawn or stale plans are counted as excluded; unauthorized relations are omitted. It neither opens plan bodies nor invents delivery. Plans are checked one at a time, so this is a refreshable planning estimate, not an atomic multi-school assessment snapshot. At most 1,000 published-plan candidates are read; source quotas and 50-step limits remain explicit.

Migration 20261017124552_AddEducationTeachingActivities adds two tables and seven Restrict paired foreign keys, without rewriting existing rows/columns or backfilling completion/provision. It constrains the public-version recipient, step-kind pairing, current/predecessor/reply references, unique assignment and separate journal/student sequences. Student sequence is explicitly non-null for student events, avoiding SQL null-check bypasses. Actor/content checks keep private handling separate and reject self-reported formal assessment completion. Semantic published-step membership and transition rules remain in the domain/application.

Private/no-store responses cover the activity interface, and generic audit excludes submitted text, private notes and event/detail bodies. This slice implements inline activities, difficulty and private follow-up, not private-library material/version/attachment grants, independent learning tasks outside plans, submitted corrections, actual formal assessment links, pause/resume scheduling or final teacher intervention decisions. AI, notifications, WeChat, policy/teaching calibration, logged-in browser and full application concurrency/load acceptance remain required.

## Native student plan extension (2026-10-18)

The one-AppID student workspace now lists plans for its selected school and opens an exact publication/step. GetMyListAsync accepts an optional school filter before the candidate quota and echoes SchoolId. GetMyActivitiesForSchoolAsync adds an explicit school check before body delivery/provision; the original GetMyActivitiesAsync and OpenMyAsync routes remain unchanged. The activity interface now has ten operations, preserving its original nine. No schema, permission or dependency changes are required.

The native view projects only student content/events, material availability and the matching teacher-handling time. MaterialsAvailable is separate from the derived activity state and from the student's own difficulty. Formal activities link to the exact real recipient and cannot self-report start/completion; their sealed label comes from actual assessment facts. The existing service timing rules remain authoritative: a step due date is not a new hard progress cutoff.

Unshared text and a retry body live only in page memory. Persistent recovery stores school/plan/activity/operation identifiers under the existing app/account scope. Read and receipt recovery use TeachingPlanView; writes also require LearningParticipate. Losing write permission does not fabricate a read prohibition. Hide or actual identity/authority loss drops private input and retry payload. A replaced publication may reject its detail while its original operation remains recoverable under current student authority; the page creates the recovery handler before the detail read and never silently switches versions or bases. Fresh-context responses and late modal/download callbacks are guarded. Actual WeChat/SDK/WXML/device acceptance remains separate from Page-script, signed local HTTPS and database evidence.
