# Student image editing and explicit local-draft conflicts

Native extension, 2026-10-18: the one-AppID student workspace uses the same frozen response/upload/submission APIs. Before editing or exact retries, it explicitly explains local private storage and shared-device limits. Question drafts keep the original response revision, attempt and paper snapshot, with one bounded local entry per question. Pending commands persist before sending under the API/app/tenant/account/recipient scope. Native image copies have operation-derived paths and SHA-256/type/size checks through platform APIs; missing support fails closed without a new crypto package or a weaker digest. Upload/replacement is applied to a local draft only after its exact receipt, and still requires a question save. Local body/copy retention is logically 24 hours and checked on later use; retry does not extend it, explicit reselecting identical bytes starts a new copy lifetime. Interrupted copy timestamp writes fall back to the original operation time. Unknown references survive body expiry or logout, but lost response bodies cannot be replayed. Logout and account switch attempt only owned draft/copy cleanup; failed cleanup remains visible. Actual resource denial hides the workspace and drops protected editor memory without deleting unrelated personal drafts. Retained self-authored values grant no right to reopen a denied task; every restore first requires current server authority. Expiry hides views and allows explicit same-account login to recover drafts. This is local code/protocol verification, not actual device storage, camera/privacy approval or physical deletion acceptance under D10.

The student assessment page now uses the existing image upload, operation recovery and authorized original-download APIs. A caller-owned attempt policy read exposes the configured per-file limit, per-response count and allowed MIME types. ## Upload confirmation is separate from an answer

Students add one JPEG/PNG/WebP image at a time. Browser camera capture is a hint, not a claim of native WeChat camera support. Upload metadata and the exact operation ID are persisted before sending. An unconfirmed upload never enters the question's valid image list. A confirmed upload adds an attachment identifier to the local question draft; saving the complete question response is still required to associate it with the server answer. Sealing uses only the existing confirmed response manifest.

Replacement retains the old image until the new upload is confirmed, then replaces its position in the local list. Rotation, order and removal edit response metadata and require a question save. They never rewrite original bytes, delete an earlier response revision or change an already sealed submission. Upload retries preserve the original operation/name/type/size/hash. Refresh recovery first checks server confirmation; buffered or reselected bytes must match the original hash. A newer server answer is not replaced with an old save receipt.

The actual text/selection/blank/image editor state is shared with integration tests as a linked pure source file, without loading the WASM host into the test assembly. It clones server values before editing and retains each question's original response revision. Refreshing advances the displayed server response set but never silently advances that draft base. A changed question head, or a legacy draft with an unknown base, requires comparison and an explicit choice before saving. Changes to a different question alone do not fabricate a same-question conflict. The server's response-set CAS remains the final write barrier.

## Local buffering and cleanup

Before selecting images, the page asks the student to acknowledge this browser's buffering behavior and shared-device risk. Native IndexedDB stores the one pending operation's bytes under the account/tenant/recipient scope and exact operation ID; tab storage retains commands, unsaved responses and their base revisions. Neither raw image bytes nor a server-save claim is placed in tab JSON. This scope separates application use, not access by someone who controls the same browser profile.

The buffer has a 24-hour logical lifetime, not a promise of physical deletion while the browser is closed. Retries do not extend an unexpired entry. Expired buffers are removed on later cache use for the current account. Missing/evicted/expired buffers require reselecting identical bytes, or explicitly abandoning the upload; a retake is a new image operation. Only server-confirmed content is guaranteed across browser clearing, device changes and external interruption.

After server upload confirmation, the page first persists the recovered local draft and a cleanup marker, then removes buffered bytes. Failed cleanup retains a marker and warning for retry after refresh. Explicit abandonment also cleans its buffer without deleting saved server facts. Raw browser buffers are not erased merely because an operation is still unknown. Cache/open/transaction failures return errors rather than leaving a fake saved/uploaded result. Full logout/identity-switch interception, shared-device retention policy, camera and storage-pressure acceptance remain open requirements.

## Viewing and verification boundary

A shared accessible preview provides 100–300% zoom and preserves right-angle rotation within positive scroll bounds. Student answering, teacher grading and opened student results use the same component; their existing authorization and result gates are unchanged. Decode errors do not change upload, save, submission or score facts. Signature validation is not a full codec/OCR/calibration guarantee.

Five new integrated tests exercise actual editor state with image storage, original-operation recovery, response saves, sealing and teacher original-image reads, plus explicit same-question conflicts and configured policy isolation. Native browser harness checks use the production cache functions and synthetic Blob bytes, including actual reload, scope/operation isolation, original expiry, blocked-storage failure and cleanup. The harness adapts the JS-stream reference to inspect the Blob; it does not verify authenticated WASM/API/camera/WeChat interaction. Those gates, real image quality, large-file/device capacity and complete application concurrency remain required.
