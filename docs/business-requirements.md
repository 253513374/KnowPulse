# KnowPulse 教师出题与学生答题业务文档

日期：2026-10-23；版本：v1.2；状态：业务方向、小程序接收方式及师生关系边界已确认，其余首期方案为建议稿。

用途：重新明确产品主线、首期范围及现有系统的调整方向。

**产品主线：教师管理个人知识库，借助个人和共享资料出题，确认后发布答题任务；学生在微信小程序作答，教师查看结果。** 企业知识库的底层能力继续复用，面向用户的产品转为教师工作后台和学生答题工具。

本文以本轮用户说明为业务方向依据。目标用户、个人／共享知识库、学生小程序、不做学校管理和教师身份认证已经明确。任务面向指定学生，首期接收效果为打开小程序即可查看待答任务，不需要额外微信消息提醒。同一学生可关联多位教师，教师仅查看自己发布任务的作答结果，新加入学生不自动收到历史任务，这三条已确认。标有“建议”或“待确认”的细节尚未定稿。现有代码只是可复用基础，不代表下述目标已经实现。本轮仅整理文档，不执行功能删除或数据迁移。

## 1 已确认的业务方向

项目最初希望建设企业知识库，随后增加教师业务。现在应围绕以下需求收口：

1. 教师有自己的资料和知识库，用于备课与出题。
2. 教师可以使用个人知识库，也可以使用获准使用的共享知识库出题。
3. 教师使用 Web 后台完成主要工作，学生使用微信小程序答题。
4. 企业知识库后台转为教师工作后台，不再以企业培训管理为产品主线。
5. 不建设学校管理，不要求教师身份证、教师资格或任职资质认证。
6. 教师发布题目时指定接收学生；学生打开小程序即可查看分配给自己的待答任务，首期不做额外微信消息提醒。
7. 同一学生可以关联多位教师，各教师分别维护自己的学生名单。
8. 各教师只查看自己发布任务的作答结果，不能借师生关系查看其他教师任务的结果。
9. 新加入学生不自动收到历史任务，不因加入教师名单而自动生成旧任务指派。

保留账号登录与数据权限。这用于识别“是谁的资料、谁发布的题、谁的作答”，不属于教师资格认证。

早期仓库方案已经包含知识库、问答、AI 出题和考试，后来还扩展了学习路径及运营管理。因此本次是按用户补充的教学场景重定业务基线，不能把最早架构方案当作仍然必须完成的需求清单。

## 2 产品解决什么问题

对教师，减少从资料整理、寻找出题依据到组织题目和收集结果的重复劳动，让教师能从自己的工作区直接开始。

对学生，提供直接可用的答题入口：找到教师发布的任务、作答、提交、查看允许展示的结果。学生不需要先加入企业组织，也不需要先浏览教师的原始知识库。

首期最小闭环为：

**准备资料 → 选择出题来源 → 生成并确认题目 → 发布答题任务 → 学生作答提交 → 教师查看结果。**

“共享资料”增加可用出题来源，但不是个人资料出题的前置条件。独立 AI 聊天、员工必修阅读和运营报表均不作为完成这条流程的条件。

## 3 用户与两端分工

| 用户 | 主要入口 | 主要工作 | 权限边界 |
| --- | --- | --- | --- |
| 教师 | Web 教师后台 | 整理资料、出题确认、维护学生名单、指定学生发布任务、查看本人任务结果 | 管理自己的资料、题目和任务；只能使用获授权的共享内容 |
| 学生 | 微信小程序 | 加入教师名单、查看待答任务、作答、继续未完成作答、提交、查看个人结果 | 仅访问指派给自己的任务和本人的作答，不自动获得教师资料权限 |
| 平台维护人员 | 必要的维护入口 | 维护账号服务、文件处理、模型配置和故障恢复 | 不是教学流程中的审批人；维护操作需要受控并可追溯 |

教师可自行出题并确认，无需专职题目审核员。模型和解析服务由平台维护，教师只需获得可理解的处理状态，不必操作技术参数。

现有 Web 员工页面属于历史实现。学生端以小程序为目标，暂不继续建设两套完整学生界面；原页面是否保留兼容入口在实施时决定。

### 3.1 学生如何加入教师名单

建议采用轻量邀请方式：

1. 教师在“我的学生”中展示或分享自己的邀请二维码／邀请码。
2. 学生在小程序登录，扫码或输入邀请码，确认教师名称，填写供教师辨认的显示名称并申请加入。
3. 教师确认申请后，该学生进入自己的有效学生名单，发布任务时可以勾选。

邀请码只用于建立师生关系，不能直接获得某份试题、教师知识库或题库的访问权。教师确认的是“这是我要接收的学生”，无需学校、身份证或学籍审核。

已确认：同一学生可以关联多位教师，每位教师维护自己的名单；教师只能看到自己发布任务产生的作答与结果，不能看到该学生与其他教师的活动。首期直接选择学生即可，不增加学校组织或班级分组。

### 3.2 在名单中 不等于收到所有题目

师生关系解决“教师可以向哪些学生布置题目”，任务指派解决“这一份题实际发给谁”。发布时必须明确选择接收学生，不能因名单为空而自动发给所有用户。

例如教师甲的名单有小明、小红、小李，这次只勾选小明和小红，则仅这两人的“我的答题”出现任务。小李没有被指派，即使获得任务链接，也不能查看或作答。小明同时关联教师乙，不影响两边分别接收任务。

## 4 核心业务流程

### 4.1 教师准备出题资料

1. 教师登录，进入个人知识库，上传资料或录入正文。
2. 资料默认仅本人可见。系统显示处理中、可用或失败及重试提示。
3. 资料完成必要处理后可用于个人出题，不要求先共享给其他教师。
4. 教师可查找并选择自己获准使用的共享资料。

首期建议优先支持正文、文本、Markdown 和可提取文字的常见 PDF／Word 资料。图片扫描件、音视频解析不作为必需能力；不支持或处理失败的文件不能被标成可出题。

个人资料的“可出题”和“已共享”必须分开表达。后台可以继续使用版本与索引机制，不能将面向其他人的共享发布变成教师自用的必经步骤。

### 4.2 教师出题并确认

1. 选择本次使用的个人资料、共享资料或两者的组合。
2. 指定题型、数量和必要的出题要求。
3. AI 基于所选且有权使用的资料生成候选题，向教师展示题干、选项、答案、解析及出题依据。
4. 教师检查并编辑，删除不合适的题目，确认后保存到自己的题库；也可手工补题。

AI 结果未经教师确认不得直接发布给学生。确认由教师本人完成即可，不强制采用“编辑员送审、审核员批准”的多人流程。

一期建议以单选、多选和判断题形成客观题闭环。现有填空题能力不等于首期必须交付；主观题批阅和 AI 正式计分不进入本轮主线。

### 4.3 教师发布答题任务

1. 从已确认题目中选择内容，调整顺序、分值并预览。
2. 填写任务名称及简要说明。
3. 从自己的有效学生名单中勾选接收人，确认人数；未选择学生时不能发布。可以显式选择“我的全部学生”，不能默认对平台全员开放。
4. 发布时保存每个指定学生的任务指派记录，学生下次打开或刷新小程序即可在“我的答题”中看到待答任务。
5. 查看本任务的已指派学生、作答状态和提交结果。

“发布成功”以任务及全部选定接收人的指派记录保存成功为准，不能出现教师看到成功但部分学生没有任务的情况。“收到”表示小程序内有可查询的任务，不表示学生已经打开或读过；首期不要求微信外部通知或额外的消息中心。

统一使用“答题任务”作为业务称呼，可承载简单练习或作业。不因已有考试模块就强制教师配置复杂组卷策略、考试等级、合格线、倒计时和重考规则。需要限时测验时再启用相应设置。

发布时保存题目、答案与评分规则快照，后续修改题库不能改变学生已经收到的任务或既有成绩。发布后修订题目、停止接收作答的具体操作规则，在实施前确定。

### 4.4 学生在小程序作答

1. 使用可持续识别本人的身份登录小程序，在“我的答题”查看已指派的待答任务。
2. 打开任务详情，查看发布教师和任务说明，开始或继续作答。
3. 选择答案、翻题；已保存答案在退出后重新进入时能够恢复。
4. 确认提交，由服务端保存并按任务快照评分。
5. 查看提交成功状态，以及规则允许展示的分数和解析。

学生显示名称用于教师辨认；是否要求真实姓名待确认，不默认收集身份证、学校、学号或手机号。微信身份接入不等于实名或学籍认证。

建议首期一人一任务一次正式提交；中途退出后继续原作答，重复点击提交返回同一结果。允许重做以及保留最好分还是最后分，作为后续规则另定。

### 4.5 教师查看结果

教师查看自己发布任务的接收名单、未开始／进行中／已提交状态、得分、作答明细和错题情况。先满足“一份任务的结果看得清”，不建设跨学校报表、复杂排名或完整教学评价体系。

应答人数以本任务保存的指派名单为准，不按当前全部学生数推算。“未开始”仅表示尚未开始作答，不能当作学生未看到或提醒未送达。

## 5 业务对象与数据边界

| 对象 | 业务含义 | 首期规则 |
| --- | --- | --- |
| 个人知识库 | 教师自己维护的出题资料空间 | 默认私有；归属教师明确；其他教师不能因有同一角色而看到或修改 |
| 共享知识库 | 获授权教师可读取并用于出题的资料集合 | 共享对象及可用权限明确；共享不等于公开给学生，也不等于允许修改原件 |
| 教师题库 | 教师确认后可反复选用的题目 | 按教师归属隔离，保留出题来源；首期不另建共享题库业务 |
| 师生关系 | 教师与学生之间的教学关联 | 建议邀请申请、教师确认后生效；只确定可选择的学生名单 |
| 答题任务 | 一次面向学生发布的题目集合和作答规则 | 属于发布教师；发布快照稳定；进入方式和结果展示规则明确 |
| 任务指派 | 某份答题任务分配给某位学生的记录 | 显式保存接收人，决定学生能否在小程序看到和参加该任务 |
| 学生作答 | 某学生在某任务中的答案和提交记录 | 服务端保存；本人可恢复；他人不可读取或修改 |
| 答题结果 | 基于任务快照计算的得分及作答明细 | 教师查看本人任务的结果；学生仅查看本人被允许展示的部分 |

### 5.1 个人与共享的最小规则

- **默认私有。** 教师上传资料不能沿用企业场景下默认全员可见的策略。
- **显式共享。** 只有主动共享或获得授权的资料才进入他人的可用出题范围。首期建议支持指定教师使用，不先建设公开资源广场；共享范围仍需确认。
- **使用与修改分开。** 获准使用共享资料出题，不代表可编辑、删除原资料；生成并确认的题目进入使用者自己的题库，不反向修改原件。
- **来源选择有约束。** 用户选了哪些资料，生成过程就必须限制在这些资料及当前授权范围内；只在提示词里写“请按这份资料出题”不够。
- **撤销影响后续使用。** 取消共享后阻止新的读取和出题。建议保留已有任务及作答快照，不自动删成绩；撤销后既有题目能否再次发布，需明确规则。
- **学生访问独立授权。** 学生得到答题权限，不等于得到原资料阅读权限。若需要阅读材料，由教师明确选出允许随题展示的内容。

### 5.2 不能随收口一起削减的规则

教师不能管理其他教师的私有资料、题目、任务或学生结果。学生只能保存自己的答案，教师题库中的标准答案、解析和内部来源信息不能在答题前通过接口提前下发。

评分和结果展示均由服务端执行。不得依靠小程序本地计分产生正式成绩，也不能仅用前端隐藏答案代替权限控制。无出题依据、资料不可用、模型失败时应明确提示，保留教师已编辑内容，不产生虚假成功状态。

### 5.3 师生关系与任务指派规则

多教师关联、教师仅查看本人任务结果、新加入学生不自动接收历史任务已确认。其余细节按以下方案建议实施，标注“建议”的处理仍待确认。

- 同一学生重复申请或同一教师重复确认，不产生重复的有效师生关系；同一任务也不向同一学生重复生成待办。
- 发布时由服务端检查所选学生仍在该教师的有效名单内；名单为空或包含未获准学生时，明确提示并阻止发布，不能自动扩大接收范围。
- 发布接收名单固定保存。后来新增学生不自动收到过去的任务；需要补发时由教师显式操作，补发能力不作为当前首期必需项。
- 建议移出学生只阻止今后的选择，不自动撤销历史任务；已指派任务仍按原规则参加，原教师仍可查看自己任务的历史结果，作答和成绩不删除。移出操作应向教师说明这一点。
- 分享或转发某个任务链接不产生新指派；学生仍须属于该任务的接收名单。邀请教师名单和分享任务是两个不同动作。

## 6 建议的首期范围与减重清单

### 6.1 建议首期交付

| 范围 | 最小交付 |
| --- | --- |
| 教师工作区 | 登录后管理自己的资料、题目、发布任务和结果 |
| 个人知识库 | 上传／录入、查看处理结果、选择资料出题、默认私有 |
| 共享资料使用 | 明确授权、选择共享资料出题、禁止修改他人原件 |
| 辅助出题 | 基于选定资料生成候选题，教师编辑、确认或手工补题 |
| 学生名单 | 教师邀请、学生申请、教师确认及移出；不引入学校组织 |
| 答题任务 | 固定选题、勾选指定学生、预览发布、持久指派及发布快照 |
| 学生小程序 | 加入教师名单、查看待答任务、作答保存、继续、提交和个人结果 |
| 教师查看结果 | 本人任务的学生提交情况、得分及作答明细 |
| 基本运行保障 | 账号权限、文件和答案保护、数据备份、失败恢复 |

### 6.2 退出当前产品主线

- 学校档案、学校组织架构、教务体系、学籍管理。
- 教师身份证、资格证、任职或学校认证。
- 企业部门、岗位、职级、安全等级配置作为教师使用的前置条件。
- 岗位学习路径、员工必学／推荐知识、阅读打卡和员工成长计划。
- 学生端独立知识问答和整库浏览；学生首先需要完成教师发布的题目。

这些是产品范围决定，不表示本轮删除现有表、接口或历史数据。现有企业场景需要兼容多久，应在后续改造前另行确认。

### 6.3 保留在后台或后置

资料转换、索引处理、访问校验、模型调用和错误日志继续作为实现能力；教师界面只呈现可理解的结果与必要操作。模型目录、路由、任务阶段、评测与审计不应成为日常出题的必经页面。

复杂随机组卷、多人题目审核、填空及主观题评分、完整限时考试、复杂防作弊、跨任务分析和运营报表按实际需求后置。教师知识问答可作为备课辅助增强，不建设第二条必须先做完的产品主线。

| 目标能力 | 当前实际状态 | 调整方向 |
| --- | --- | --- |
| 教师个人知识库 | 已有知识上传、版本、附件、处理与可见范围；没有完整的教师归属和读写隔离 | 复用资料处理；补教师所有权、默认私有和跨教师隔离，不能把通用上传人审计字段当作已实施授权 |
| 共享知识库 | 企业全员／部门／角色／指定用户可见范围存在；不等于已具备共享使用规则 | 区分共享使用与修改原件，明确共享对象；不能直接用“全员”代替“共享给教师” |
| 选择资料出题 | 有授权检索、AI 候选题和来源记录；当前知识范围输入是自然语言文本 | 补个人／共享资料选择及实际检索约束，不能宣称已经只从勾选资料生成 |
| 教师确认和个人题库 | 有草稿、送审、通过／退回流程；没有完整教师题库隔离 | 复用校验与状态；教师本人确认，减少对外暴露的流程步骤，不增加专职审核岗位 |
| 师生关系 | 尚无邀请加入、教师确认和个人学生名单的完整业务 | 补轻量师生关系，不用学校或企业部门替代 |
| 轻量答题任务 | 已有指定用户考试分配、组卷、保存和评分，但空分配仍默认全员可参加 | 复用答题评分基础，补教师归属、有效学生校验和显式接收名单；空名单必须拒绝，不能沿用全员默认值 |
| 学生结果和答案保护 | 有本人作答校验；当前试卷 DTO 仍映射正确答案、解析与来源，结果可见性未在返回端充分落实 | 学生接口按作答阶段和展示规则裁剪，教师只能查询本人任务结果；属于真实学生使用前的阻塞项 |
| 小程序 | 现有为员工学习原型，数据和计分本地演示，未接真实登录和业务 API | 复用原生工程与答题交互，改为学生任务流程并接真实服务；不保留五个员工导航作为必需范围 |

此外，过期的进行中作答恢复、处理完成状态真实性仍需核验和修正，不能把现有“考试可运行”或“已索引”标记直接作为新业务上线验收结果。

目标默认私有与现有 [ADR 0002 默认全员可见](adr/0002-default-guided-upload-visibility.md) 不一致，实施教师场景前必须重新记录该决定并调整迁移策略。现有 [原子发布](adr/0005-atomic-knowledge-publish-with-explicit-access-policy.md) 和 [可靠索引](adr/0006-recoverable-knowledge-index-job-execution.md) 的一致性保障可以复用，不因界面简化而移除。本轮不修改已采纳 ADR，也不将教师业务标为已实现。

## 8 建议的最小页面

教师 Web：**我的资料、共享资料、出题与题库、我的学生、答题任务**。这些是工作入口，可合并为同一工作区的标签或步骤，不要求五个独立模块；结果从对应任务进入即可。

学生小程序：**我的答题、任务详情、答题、提交结果**。在“我的答题”提供扫码／输码加入教师的入口，显示教师确认状态；个人显示名称放在页内维护即可，不要求先建设完整个人中心或学习路径。

页面结构是收口建议，后续按真实操作验证，不以原有菜单数量作为需求。

## 9 建议的首期验收场景

1. 教师 A 不配置学校和企业组织、不提交身份证或资格证明，也能管理自己的资料并开始出题。
2. 教师 A 的个人资料，教师 B 不能通过列表、直接 ID、附件地址或 AI 检索读取，也不能修改、删除。
3. A 将资料授权给 B 后，B 可在约定范围内据此出题，但不能修改 A 的原件；未授权教师和学生不能读取。
4. 教师选定一份个人资料和一份共享资料后，候选题依据只来自所选授权资料；无依据或处理失败时明确提示，不编造成功结果。
5. AI 题经教师本人检查、必要时修改并确认后才能发布，无需另一个审核员审批。
6. 教师名单有三名学生，只指派其中两人时，仅这两人在小程序看到待答任务；第三人通过转发链接或修改任务 ID 也不能进入作答。
7. 学生答题前，网络响应不包含正确答案、解析和教师私有原始资料；重复进入能恢复本人已保存答案。
8. 重复点击提交只产生一次有效结果，得分依据发布快照；学生只能看到本人按规则可见的结果。
9. 教师只看到本人任务的学生结果，不能改请求参数查询其他教师或学生的私有记录。
10. 题库或共享资料后续变化，不静默改写已发布题目、既有答案和成绩。新发布的取用规则与历史记录处理规则分别验证。
11. 新增学生不自动补发旧任务，移出学生不删除历史成绩；同一学生可以分别收到两位教师指派的任务，教师互相看不到对方任务的结果。
12. 不选择学生、选择其他教师名下且未与本人建立有效关系的学生，均不能发布；指派成功后任务可在小程序持续查询，无需依赖微信消息提醒。

## 10 实施顺序与待确认事项

### 10.1 按业务闭环实施

1. **先跑通个人资料到学生结果。** 教师归属和隔离、个人资料、出题确认、学生名单、定向发布、学生待办与真实作答、教师看结果串成一条链。学生答案保护是这一阶段的基础，不推迟处理。
2. **再跑通共享资料出题。** 补共享授权、资料范围选择、取消共享后的后续使用边界，并以两个教师账号验证。
3. **完成首期验收后再扩展。** 验证中断恢复、重复提交、历史快照和真实微信环境；按反馈决定是否增加限时、重做、更多题型和统计。

个人知识库与共享知识库均属于已明确的产品目标，建议首期覆盖前两步。具体分批交付范围仍需确认；不设未经评估的工期或承诺。

### 10.2 尚需确认的少量规则

| 事项 | 首期建议 | 待确认的分界 |
| --- | --- | --- |
| 共享范围 | 先向指定教师授权，不建公开资源广场 | 是否需要所有注册教师可用的公共资料池；谁可发布和撤销 |
| 师生关系建立 | 邀请二维码／码申请，教师确认 | 是否采用教师确认；是否必填姓名。多教师关联已确认，不再待定 |
| 提交与结果 | 每人一次正式提交；交卷即确认成功 | 分数、答案与解析是立即显示、任务结束后显示，还是由教师选择 |
| 共享撤销与已发内容 | 停止后续读取和出题，保留已发任务与成绩 | 既有题目能否再次发布；任务发布后修改或停止接收的规则 |
| 历史企业能力 | 暂停继续扩建，保留现有数据 | 是否仍有企业用户需要兼容；是否及何时隐藏旧入口 |

学生打开小程序查看待答任务、不需要微信消息提醒，以及多教师关联、各教师仅查看本人任务结果、新加入学生不自动接收历史任务均已确认。其余规则未确认前保持显式待定，不将当前考试参数或企业权限默认值直接当作教学需求。
